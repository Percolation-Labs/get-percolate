# percolate

An AI workflow engine in Postgres — DAG workflows, agents, graph and semantic
query, all as rows.

```bash
cat > percolate-values.yaml <<EOF
secrets:
  postgresPassword: $(openssl rand -hex 24)
  authenticatorPassword: $(openssl rand -hex 24)
  workerPassword: $(openssl rand -hex 24)
  jwtSecret: $(openssl rand -hex 32)
  s3Key: $(openssl rand -hex 16)
  s3Secret: $(openssl rand -hex 24)
  openaiApiKey: "${OPENAI_API_KEY:-}"   # the Agent Runtime's model key
  llmApiKey: "${OPENAI_API_KEY:-}"      # what embedding steps resolve
EOF
helm install percolate oci://ghcr.io/percolation-labs/charts/percolate \
  -n percolate --create-namespace -f percolate-values.yaml
```

The four passwords are **required and never generated by the chart** — see
*Why nothing is auto-generated* below, because it is the one design decision
here that surprises people. They are hex because the services connect with a
`postgres://` URL and a base64 `/` ends the password inside it; the chart
refuses such a password at render time.

**Keep the file.** `helm upgrade percolate … -f percolate-values.yaml` reuses
it; running the `openssl` lines again writes new passwords into the Secret
while the database keeps the ones it was initialised with, and every service
then fails with `password authentication failed`. `jwtSecret` is also what you
sign tokens with (`percolate auth token --secret …`).

`agent:` workflow steps need one more value once there is a user to act as:
`secrets.workerApiKey`, a long-lived token for the http worker to present to
the Agent Runtime —
`percolate auth token --email you@example.com --ttl 31536000 --secret <jwtSecret>`.
The CLI's default lifetime is an hour.

## What it installs

| | |
|---|---|
| `StatefulSet/…-postgres` | PG19 with the extensions baked in. **Installs itself on first start** — the bootstrap is in the image, so there is no init ConfigMap to keep in step with the schema. |
| `Deployment/…-postgrest` | the REST/RPC surface, RLS-filtered |
| `Deployment/…-content` | uploads, ingestion, serving bytes back |
| `Deployment/…-agent` | agents, AG-UI streaming, delegation |
| `Deployment/…-worker-<name>` | one per entry in `workers`, one per queue |
| `StatefulSet/…-minio` | object storage, for getting started |

No CRDs, and no operator. The only custom resources are KEDA's, emitted **only**
if you turn autoscaling on.

## Three ways to get the chart

| | |
|---|---|
| **OCI** (preferred) | `oci://ghcr.io/percolation-labs/charts/percolate` — no repository index, no DNS, no Pages build. Helm 3.8+, Flux `OCIRepository`, Argo all read it. |
| **Git** | point straight at `charts/percolate` in this repo. Nothing is published at all, so nothing can be stale. |
| **Classic repo** | `helm repo add percolate https://percolation-labs.github.io/get-percolate/charts` — familiar, and the one that depends on a domain, a Pages deploy and a correctly merged `index.yaml`. |

The ordering is deliberate. A classic Helm repo is a URL, so it inherits every
failure mode of the thing serving it; a chart nobody can install because a CNAME
is missing is worse than one extra command to learn.

### Why nothing is auto-generated

Most charts generate a missing password with `randAlphaNum`. This one refuses,
and the reason is specific to GitOps: a generated value differs between
`helm template` and `helm install`, and between a dry run and the apply that
follows. Flux and Argo both diff continuously, so a self-generating secret makes
that diff **permanent** — the controller reports drift forever, or worse,
"heals" it by rewriting the database password out from under a running
StatefulSet. Failing at render time with a named value is the smaller cost.

Point `secrets.existingSecret` at something you already manage (External
Secrets, Sealed Secrets, SOPS) with keys: `postgres-password`,
`authenticator-password`, `worker-password`, `jwt-secret`, `s3-key`,
`s3-secret`, and optionally `llm-api-key`, `openai-api-key` and
`worker-api-key` — without those three, embedding, agent turns and `agent:`
steps respectively fail at call time, and everything else runs.

## Worker pools

`workers` is a **list**, because `queue` is the only signal that both
`claim_task` and an autoscaler see. One pool per queue is how a slow model
endpoint stops starving a fast ingestion queue.

Two pools ship by default: `http`, for steps that leave the machine, and
`ingest`, which is not optional if anyone uploads a file. The ingestion
workflow puts both of its steps on the `ingest` queue, so with no pool for it
`POST /files` returns 201 and the file is never read — nothing errors, the
`parse` task simply stays `ready`. Replacing this list replaces both, so keep
`ingest` in whatever you set.

```yaml
workers:
  - name: http
    queue: http
    autoscaling: {enabled: true, minReplicas: 0, maxReplicas: 20, queueDepthPerPod: 25}
  - name: ingest
    queue: ingest
    replicas: 1
```

With `autoscaling.enabled`, the chart emits a KEDA `ScaledObject` whose trigger
is a SQL query:

```sql
select workflow.queue_depth('http')::int
```

`queue_depth` counts tasks that are ready to claim now (`run_after <= now()`)
**and** tasks already running — not CPU, and not the row count of `workflow.tasks`, because a task
blocked on a dependency is not work anyone can do, while a running one is work
a pod is holding and scaling that pod away would interrupt it. `minReplicas: 0`
is legitimate: nothing ready and nothing running, no pod.

## Bringing your own Postgres

```yaml
postgres: {enabled: false}
externalDatabase:
  host: pg.internal
  database: percolate
```

You are then responsible for the bootstrap that the image normally does —
[`install.sh`](../../install.sh) and then [`bootstrap.sql`](../../bootstrap.sql),
which creates the roles and the cron jobs. Note that **pg_cron must be
preloaded** (`shared_preload_libraries=pg_cron`, `cron.database_name=<db>`) or
scheduled workflows, the stale-task reaper and every timer step silently never
fire.

## Values

Every key is documented inline in [`values.yaml`](values.yaml). The ones that
decide whether this works at all:

| | |
|---|---|
| `secrets.*` | the four passwords are required; see above |
| `secrets.openaiApiKey`, `secrets.llmApiKey` | the model key and the embedding key; empty means agent turns and embedding fail at call time |
| `secrets.workerApiKey` | the token `agent:` steps present to the Agent Runtime; empty means every agent step fails |
| `secrets.s3Key`, `secrets.s3Secret` | object-store credentials; empty falls back to MinIO's well-known defaults |
| `agent.env` | keys for providers other than OpenAI (`ANTHROPIC_API_KEY`, …) |
| `postgres.extraArgs` | preloads pg_cron. Emptying it disables scheduling, silently as far as the workflow tables are concerned |
| `objectStorage.external.endpoint` | real object storage; leave empty for the bundled MinIO |
| `workers[]` | one entry per queue |
| `ingress.hosts[].service` | which of the three surfaces a host routes to — they are different audiences |
